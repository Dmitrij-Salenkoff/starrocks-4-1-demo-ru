# 01 · От платёжного события до ежедневной витрины выручки

**Результат:** представление, к которому финансовый аналитик может обратиться утром. Возврат во вторник способен увести показатель за вторник в минус, даже если покупка была в понедельник. День, когда банк отклонил единственный платёж, тоже должен попасть в отчёт. На работу с данными и планом запроса отведите 40–55 минут.

## Поднять стенд

Потребуются Docker с Compose и uv. В каталоге этого урока выполните:

```sh
docker compose up -d --wait
uv run --project ../.. python ../../tools/lab.py setup
```

В DataGrip выберите драйвер MySQL и подключитесь к `127.0.0.1` на порт `9030` под пользователем `root` с пустым паролем. В контейнере уже есть консольный клиент:

```sh
docker compose exec starrocks mysql -uroot -h127.0.0.1 -P9030 sr01
```

Команда setup пересоздаёт таблицу `sr01.payment_events` и пустое представление-заготовку `sr01.daily_revenue`. Её можно повторить, чтобы начать с исходных данных. Сохраните свой SQL в отдельном файле. В таблице уже лежат все семь событий задачи.

## Проследить путь запроса

Клиент подключается к frontend (FE). Этот узел ведёт каталог, разрешает имена и типы, строит план и распределяет его фрагменты. Backend (BE) хранит колоночные данные на локальном диске, сканирует их и выполняет операторы плана. На стенде оба процесса работают в одном контейнере в режиме shared-nothing. В архитектуре shared-data постоянные данные хранятся в объектном хранилище или HDFS, а вычисления выполняют compute nodes. Если клиент подключается, а чтение таблицы падает, эти роли подсказывают, где искать причину.

```sql
SHOW FRONTENDS;
SHOW BACKENDS;
SHOW CREATE TABLE sr01.payment_events;
SELECT event_id, event_day, order_id, event_type, amount_minor
FROM sr01.payment_events ORDER BY event_id;
```

Найдите у FE порт 9030, а у BE проверьте признак Alive. В DDL указано `DUPLICATE KEY (event_id)`: такая таблица сохраняет все поступившие строки, включая повторения ключа. В этом наборе уникальность идентификаторов обеспечивает источник. Повторная отправка того же INSERT способна удвоить сумму платежа. Для одного локального BE мы задали один хеш-бакет и одну реплику.

## Договориться о смысле показателя

Одна входная строка описывает **событие платежа**, одна выходная строка — **день, за который пришло хотя бы одно событие**. Один заказ может дать списание сегодня и возврат завтра. Дата уже приведена к учётному дню в UTC. Суммы положительные, в центах США. Возврат учитываем в день возврата. В рамках задачи слово «выручка» обозначает движение денег по этим операциям. Для бухгалтерской отчётности понадобится отдельное определение показателя.

| event_type | capture_count | gross_minor | refund_minor |
| --- | ---: | ---: | ---: |
| capture | 1 | amount_minor | 0 |
| refund | 0 | 0 | amount_minor |
| decline | 0 | 0 | 0 |

Для каждого дня `net_minor = gross_minor - refund_minor`. Если все платежи за день отклонены, его группа получит нули. Если событий вообще не было, группа не возникнет. Для сплошного календаря пришлось бы присоединить таблицу дат. Центы сохраняем целыми вплоть до вывода отчёта в долларах.

## Практика

1. Найдите обе операции заказа 502. Запишите даты списания и возврата. Вручную посчитайте итог за оба дня с учётом других заказов. Объясните знак суммы за вторник.
2. Выполните заведомо ошибочный запрос ниже. Он принимает сумму любого события за приток денег. Назовите два типа событий, для которых это неверно, и объясните результат за 14 января.

   ```sql
   SELECT event_day, SUM(amount_minor) AS candidate_net
   FROM sr01.payment_events GROUP BY event_day ORDER BY event_day;
   ```

3. В редакторе SQL напишите `CREATE OR REPLACE VIEW sr01.daily_revenue AS ...`. Верните пять столбцов с именами из таблицы ниже. Положите каждую составляющую в отдельную условную сумму, а разность вычислите во внешнем запросе. Сохраните все типы событий при группировке. Выведите результат командой `SELECT * FROM sr01.daily_revenue ORDER BY event_day;`.
4. Откройте физический план. Найдите чтение исходной таблицы и оператор агрегации. Объясните одним предложением, почему имя представления может исчезнуть из плана. Посмотрите, где в вашей сборке оказался предикат по дню.

   ```sql
   EXPLAIN SELECT event_day, net_minor
   FROM sr01.daily_revenue WHERE event_day = '2026-01-13';
   ```

5. В каталоге урока запустите `uv run --project ../.. python ../../tools/lab.py check`. Проверка сверяет число строк и каждую сумму. С исходным пустым представлением она ещё не пройдёт.

| event_day | capture_count | gross_minor | refund_minor | net_minor |
| --- | ---: | ---: | ---: | ---: |
| 2026-01-12 | 2 | 20000 | 2000 | 18000 |
| 2026-01-13 | 1 | 6000 | 8000 | -2000 |
| 2026-01-14 | 0 | 0 | 0 | 0 |

## Разбор решения

После собственной попытки откройте `solution.sql`. Примените эталон командой `uv run --project ../.. python ../../tools/lab.py solve` и ещё раз запустите check. Внутренний запрос сохраняет семь событий и образует три группы. Каждое выражение CASE даёт одной составляющей нужный вклад, остальным — ноль. Внешний запрос возвращает обе положительные суммы и один раз вычитает возвраты. Команда `CREATE OR REPLACE VIEW` сохраняет определение запроса. При чтении представления StarRocks обращается к исходным данным. Повторный запуск решения заменяет определение.

Сверка за весь период: списания дали 26 000 центов, возвраты — 10 000, остаток — 16 000. Одной такой сверки мало. Если отнести возврат 8 000 на понедельник, итог за период сойдётся, хотя обе дневные строки окажутся ошибочными.

## Вопросы для самопроверки

- Что подтверждает успешное подключение к порту 9030? Как отдельно проверить BE?
- Почему фильтр, который оставляет только списания и возвраты до GROUP BY, убирает 14 января?
- Источник повторно прислал событие 2. Что сохранит таблица? Какие показатели изменятся? Какой идентификатор потребуется для защиты от повторной доставки?
- Почему логическое представление покажет новый платёж без обновления по расписанию? Какой оператор плана прочитает его?
